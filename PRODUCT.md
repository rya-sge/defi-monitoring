# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Users

Primary: a risk team / analysts who follow **third-party** Morpho positions (not only their own) — several people reading the same alerts and deciding together whether a position stays, shrinks or exits. They work from a desk, with the CLI available in a terminal next to the browser, and they arrive already knowing the vocabulary (vault, adapter, LLTV, health factor, bad debt).

## Product Purpose

`riskdep` answers one question about a DeFi position on Ethereum, centred on Morpho: *what is my real exposure, and has anything changed since the last block?* Three outputs: a batch risk report ending in STAY / REDUCE / EXIT, a block-by-block watch of a Morpho Vault V2 for a depositor, and a watch of every Blue borrow and Vault V2 deposit of one address. Success is an analyst noticing a risk-increasing change (upgrade, oracle drift, bad debt, timelock-free admin power) before it costs money, and trusting the number enough to act on it.

## Positioning

The dependency stack is made explicit and traversable rather than summarised into a score: the position is decomposed into typed layers (actor, pool, asset, oracle, admin, external), a shock is propagated along those edges, and the verdict is accompanied by the chain of reasoning that produced it. Every threshold and assumption is declared in `riskdep/registry.json` with its basis, so a number on screen can be traced to a stated prior rather than to a model nobody can inspect. All data comes from keyless public sources, so a reader can reproduce any figure.

## Operating Context

- The CLI is the primary tool; the SPA (`web/`) is a browser view over the same three outputs, reading artifacts the CLI wrote (`out/report.json`, `out/graph.json`, `out/watch-*.jsonl`).
- The API never hosts the watcher: `watch` is its own long-running process; the web UI polls `/api/alerts` with a block cursor via SSE.
- Three routes: `/` (position report), `/graph` (dependency graph), `/watch` (live alert stream, filterable by minimum level).
- `VITE_USE_MOCKS=true` is the default, including with no `.env`: the UI runs on committed fixtures in `web/src/mocks/` with no backend.
- Alert triage is a shared ritual: each alert level has a documented meaning and response in `docs/alert-runbook.md`.

## Capabilities and Constraints

- Three alert levels — `info` / `warn` / `critical` — are a contract with the runbook and the `.jsonl` artifacts, not a visual choice.
- `inf` / `nan` arrive as `null` (a health factor with no debt, a risk multiple with no expected loss); every value on screen can legitimately be absent and renders as an em dash.
- Payload types in `web/src/api/types.ts` are hand-written from real CLI output; a payload change must update the type and the fixture together.
- Two different graph shapes reach one renderer: `/api/graph` (six capitalised kinds) and the serialised networkx graph embedded in a report (lowercase kinds, `from`/`to` edges).
- Free public RPC limits are visible in the product: state is servable only ~64–90 blocks back, reorgs deeper than 2 blocks are not handled, some ranges are refused — so "not checked" and "could not be read" are normal states the UI must be able to say.
- The current colour tokens are duplicated in three places on purpose (`riskdep/graph.py`, `web/src/lib/graph.ts`, `web/src/styles.css`) so the SPA and the CLI's standalone HTML read as one tool; a colour change touches all three files. This is a coupling to respect, not a binding identity — see Brand Commitments.
- Mobile is not a known usage context; nothing has established it either way.

## Brand Commitments

None binding. The author stated explicitly that nothing in the current visual vocabulary is locked — palette, typography and layout are all open. The only durable requirement is that the three alert levels stay distinguishable and keep their meaning.

## Evidence on Hand

- Real outputs: `out/report.json`, `out/graph.json`, `out/watch-*.jsonl` (git-ignored, regenerated by the CLI); committed copies in `web/src/mocks/report.json` and `graph.json`.
- Recorded on-chain ranges in `data/replay/` and an analyse snapshot in `data/snapshot/` make every figure reproducible offline; 126 offline tests run against them.
- Two `critical` entries in `web/src/mocks/alerts.ts` are **invented**, modelled on `docs/alert-runbook.md` because no recorded run contains one. They must never be cited as a real event payload.
- No users, customers, testimonials, pricing or deployment exist. Do not fabricate any.

## Product Principles

1. A number on screen is traceable: every threshold has a declared basis, every verdict shows the chain that produced it.
2. Absence is information. "Not checked", "could not be read" and an empty value are first-class states, never hidden behind a plausible-looking figure.
3. Severity drives attention. What an analyst must act on now outranks what is merely true.
4. The CLI and the browser are one tool: the same vocabulary, the same figures, no divergence in meaning between them.
5. Pure rules, I/O at the edges — the UI presents a decision it did not make.

## Accessibility & Inclusion

The incumbent palette was chosen as a colour-blind-safe set (Okabe-Ito) because severity is encoded in colour; whatever replaces it must keep severity legible without colour alone.
